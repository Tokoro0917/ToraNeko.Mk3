# KOGUMA からの移植：棚卸しと判断

ToraNeko.Mk3 のファームウェアは、KOGUMA.MkIIl のコード（[../reference/koguma-mkiil/](../reference/koguma-mkiil/)）をベースに作ります。
このファイルは「KOGUMA のどの機能を持ち込み、どれを持ち込まないか」を決めるための表です。コードはここには書きません。

> **参照している KOGUMA のコード**：2026-10-13 に最新版（`2b70f1d3`）へ更新した（それまでは 2026-09-25 の `e456da3`）。
> 最新版ではモード0が「フラグの組み合わせ」（`Maze_Search(flags)`、`SEARCH_SLALOM` / `SUCTION` / `KNOWN` / `DIJKSTRA` / `SHORTEST` など）に書き直され、番号が変わっている。
> 下の C の表の「モード0 No.○」は**古い番号**のまま残している。新しい番号との対応は C の表のすぐ下を参照。

## 方針

- **使っていない機能は持ち込まない。** 呼ばれていない関数、空の分岐、コメントアウトされたコードは移植しない
- **テスト・デバッグ用の機能は、ToraNeko でも使うと決めたものだけ持ち込む**（下の B・C で判断する）
- **パラメータ違いのコピーは 1 つにまとめる**（下の D）
- 実装は README の「実装の進め方」のステップ順に 1 つずつ行う。各ステップで、このファイルの該当行を読み、判断を「確定」にしてから実装する

## 調べ方

`main()` と割り込みの入口（`TIM6_DAC_IRQHandler`、`HAL_ADC_ConvCpltCallback`、`DMA2_Stream0_IRQHandler`）から、関数呼び出しをたどって届くかどうかを調べました。
コメントアウトされた呼び出しは「呼んでいない」として扱っています。対象は `Core/Src/` の自作ファイル（CubeMX の生成コードを除く）です。

| ファイル | 使われている関数 | 使われていない関数 |
|---|---|---|
| `Maze.c` | 27 個（約 1830 行） | 6 個（約 120 行） |
| `Move.c` | 8 個（約 680 行） | 3 個（約 140 行） |
| `motor.c` | 25 個（約 790 行） | 2 個（約 80 行） |
| `PL_encoder.c` | 8 個 | 2 個 |
| `lsm6dsr.c` | 5 個 | 4 個 |
| `UI.c` | 11 個 | 3 個 |
| `PL_sensor.c` | 2 個 | 1 個 |
| `Wallsensor.c` / `Failsafe.c` / `LOG.c` / `PL_timer.c` | すべて | なし |
| `main.c` | `main()` が約 1770 行（モードごとの分岐） | — |

呼ばれていない関数は少なく、全体の約 7% です。量として大きいのは「`main.c` のモード分岐」と「パラメータ違いのコピー」のほうです（C・D）。

## C. モード単位の整理

KOGUMA のモード表（[reference README](../reference/koguma-mkiil/README.md) の「メイン動作モード」）を、ToraNeko で使うかどうか判断します。

| KOGUMA | 内容 | 提案 | 判断 |
|---|---|---|---|
| モード0 No.0 | 空 | 持ち込まない | **確定**：持ち込まない |
| モード0 No.1, 2 | スラローム探索（吸引なし）＋全面探索あり／なし | 吸引ありの探索だけにするなら持ち込まない（`Robot_Maze_Sula_Action` ごと不要になる） | **確定**：持ち込む。全面探索は持ち込まないので No.1 と No.2 は同じになり、「吸引なしの探索」1 つにする |
| モード0 No.3, 4, 5 | 吸引探索（全面探索なし／あり／復路後に最短） | 持ち込む。3 つを「全面探索するか」「最後に最短を走るか」の設定違いとして 1 つの探索処理にまとめる | **確定**：持ち込まない（`Robot_Maze_Suction_Action` は不要） |
| モード0 No.6 | 既知区間加速の探索（`Robot_Maze_Pass_Action`）＋最短 | 持ち込む | **確定**：持ち込む（吸引あり） |
| モード0 No.7 | ダイクストラ誘導の未知壁探索（`Maze_Unknown_Wall_Scan`） | 大会で使ったかどうかで判断 | **確定**：持ち込む（吸引あり） |
| モード1 | 最短走行（速度・加速度違い 9 種、BFS 8 種＋ダイクストラ 1 種） | 経路生成を BFS かダイクストラのどちらかに決め、速度は表から選ぶ形にする | **確定**：経路はダイクストラだけ。速度は表から選ぶ |
| モード2 | サーキット（未実装） | 持ち込まない | 未 |
| モード3 | 固定速度の最短（デバッグ用） | モード1 の表に「直線最高速＝コーナー速度」の行を足せば済むので、モードとしては持ち込まない | 未 |
| モード4 | 基本調整（センサ表示、直進、旋回、スラローム、斜め、吸引待機、壁合わせ、ログ出力） | 持ち込む。ToraNeko の立ち上げ（ステップ 1〜7）で順番に必要になる | 未 |
| モード5〜9 | 速度別の旋回パターンテスト（速度 5 種 × 旋回 7 種。一部は空） | 「速度」と「旋回の種類」を選んで走らせる 1 つのテストモードにまとめる。空の分岐は持ち込まない | 未 |

**最新の KOGUMA のモード0との対応**（ToraNeko の `sys/explore.c` も、KOGUMA と同じく「フラグの組み合わせ」で探索の種類を選ぶ形にする）

| 古い番号（上の表） | 最新の番号 | フラグ | ToraNeko |
|---|---|---|---|
| No.1, 2 | No.1（往復）、No.2（全面探索）、No.3（片道） | `SLALOM` | 吸引なしの探索として持ち込む（全面探索の No.2 は持ち込まない） |
| No.3〜5 | No.4、5、9 | `SUCTION` | 持ち込まない |
| No.6 | No.7、10 | `SUCTION \| DIJKSTRA \| KNOWN` | 既知区間加速は `KNOWN` として持ち込む |
| No.7 | No.6（既知区間加速なし）、No.7（あり） | `SUCTION \| DIJKSTRA` | 未知壁探索は `DIJKSTRA` として持ち込む |
| — | No.8〜10 | `SHORTEST`（スタートに戻ったあと最短走行まで続けて走る） | ステップ9で決める |

### 迷路の大きさとゴール

| 項目 | 決定 |
|---|---|
| 迷路の大きさ | **32×32**（ハーフサイズ）。KOGUMA は 16×16 で、ゴールは中央 2×2 固定 |
| ゴールの位置・大きさ | **機体の操作で選べるようにする**（大会ごとに違うため）。選んだ値は Flash に保存する。操作方法はステップ9（`sys/ui.c`）で決める。`maze/` はゴールの座標と大きさを引数で受け取る |

| 機能 | 使っている場所 | 提案 | 判断 |
|---|---|---|---|
| BFS 歩数マップ（`Maze_Step_Calculate`） | 探索（足立法） | 持ち込む | **確定**：持ち込む |
| BFS による最短経路（`Maze_Shortest_Calculation`） | モード1（8 種）。既知区間加速の探索は `Known_Pass_Generation` を使うので関係しない | ダイクストラに一本化するなら不要 | **確定**：持ち込まない（`Shortest_Pass_Compression*` も） |

### 既知区間の経路（`Known_Pass_Generation`）を移したときに変えたこと

| KOGUMA | ToraNeko（`maze/path.c` の `path_make_known`） |
|---|---|
| 動きを数字で表す（`2` = 1 区画直進、`-2` = 左、`-8` = U ターン など） | 動きに名前を付けた（`MOTION_STRAIGHT`、`MOTION_TURN_LEFT`、`MOTION_UTURN` など）。直進の長さは半区画の数で持つ |
| 2026-10-09 から、既知区間では大回りを使わず、曲がりはすべて小回りスラローム（`KNOWN_PASS_BIG_TURN 0`） | 同じ。既知区間の経路は、直進と小回りと U ターンだけ |
| 先頭は `-1`、終端は `0`（2026-10-13 の修正で、最短経路用の「直進があるふり」の値を置かないようにした） | 同じ。既知区間は区画の入口から始まり、まだ見ていない区画の入口で終わる |
| 斜めへの変換（`Known_Pass_Compression_NANAME`）も計算しているが、走る側は使っていない | 持ち込まない |
| 経路を作るときに `Maze_Wall_Update` を呼んで、ロボットの位置を実際に動かしてから元に戻している | 位置は関数の中の変数だけで動かす。迷路の情報もロボットの位置も書き換えない |

### 最短経路（`Maze_Dijkstra_Calculation`、`Shortest_Pass_Compression`、`_NANAME`）を移したときに変えたこと

| KOGUMA | ToraNeko（`maze/dijkstra.c`、`maze/path.c` の `path_make_shortest`） |
|---|---|
| ダイクストラの結果を、たどりながらそのまま動きの数字（`-2`、`-3` など）にしている | ダイクストラは「通る区画の並び」だけを返す。区画の並びを動きにするのは `path.c`。未知壁探索（No.7）でも同じ区画の並びを使える |
| ゴールは中央の 2×2 固定（入口 8 か所） | ゴールは任意の長方形。外側との境目で壁のないところを全部入口にする |
| 経路の先頭と終わりに「直進があるふり」の値（`1`）を置いて、最初と最後のターンも大回り・斜めにしている | 先頭はスタートの区画を抜ける直進（2 半区画）から始まる。終わりは、ゴールの最初の区画の真ん中まで半区画進む直進を足す。そのため、どちらも本物の直進として扱える |
| 点 12 方向ぶんの処理を、ほぼ同じコードで 12 回書いている | 「点から向き dir に進むと、どの点に着いて、どの区画を通るか」を `move_from()` にまとめ、8 方向をループで回す |
| 斜めへの変換で、使い終わった場所に `-1` を書いて飛ばしている | 動きを新しい経路に写しながら変換する。使い終わった動きは、番号を進めて飛ばす |
| コスト `ST_COST 5`、`DIAG_COST 3`、`CON_COST 2` | 同じ値（`COST_STRAIGHT`、`COST_DIAGONAL`、`COST_CONTINUE`）。調整するときは `dijkstra.c` の先頭を変える |
| 2026-10-13 の修正：壁の点を「どちら向きに通り抜けているか」の 2 つの状態に分け、通り抜けた先の区画を通る 3 本だけに進む。ゴールの入口には外向きの向きを持たせる（向きを分けないと「区画に入って横に抜け、同じ区画に戻る」走れない道ができる） | 同じ（`state_t` = 点 + 通り抜ける向き）。ToraNeko のランダム迷路 2000 個のテストで、直す前は 7 個で走れない道ができ、直したあとは 0 個 |

### 未知壁探索（`Maze_Unknown_Wall_Scan` と `main.c` の `Maze_Search_Unknown_Walls`）を移したときに変えたこと

最新の KOGUMA（2026-10-13）の流れに合わせた。ダイクストラは止まっているときだけ計算する（走りながらだと KOGUMA で約 9ms、その間に約 1cm 進んでしまう。ToraNeko は 32×32 でクロックも遅いので、もっとかかる見込み）。

| KOGUMA | ToraNeko（`maze/search.c`） |
|---|---|
| 止まって計算する：ゴールに着いたとき、U ターンのとき、目標に着けなかったとき、見に行った壁が実際にあったとき（経路がふさがれた。次の区画の真ん中で止まり、前に壁があれば壁合わせ） | 同じ。計算は `search_plan_unknown_walls()`（重い）。止まっているときに呼ぶ |
| 見に行った壁がなかったときは止まらず、同じ経路で次の未確認の壁へ（`Maze_Unknown_Wall_Scan`） | 同じ。`search_check_unknown_walls()`（軽い）で覚えた経路を見直す |
| 経路がふさがれたかは、見に行った壁だけを調べる（`Maze_Unknown_Wall_Is_Wall`） | 経路の上の**全部の壁**を調べる。見に行く途中で、経路の上の別の壁があるとわかった場合もふさがれたとする（見に行った壁しか調べないと、ふさがれた経路の残りの壁を見て終わり、もっと速い道を見逃すことがある） |
| 見に行く区画は、壁を通り抜けた先（ゴール側）の区画 | 壁のスタート側の区画（その壁の手前）。まだ入ったことのない区画なので、入れば必ずその壁を見られる |
| 経路の未確認の壁がなくなったら、スタートへ戻る | **その場で止まって最短経路を計算してから**、スタートへ戻る（2026-10-13 に決定） |

**ToraNeko の未知壁探索の流れ**（ステップ9の `sys/explore.c` はこの順に書く）

| # | すること | 使う関数 |
|---|---|---|
| 1 | 行き：スタート → ゴール（足立法、見た区画は既知区間でまとめて走る） | `search_set_target`、`search_update_step_map`、`search_decide_action`、`path_make_known` |
| 2 | ゴールで止まって、未知壁探索の経路を計算する | `search_plan_unknown_walls` |
| 3 | 覚えた経路を見直す（`search_check_unknown_walls`）<br>・見ていない壁がある → その手前の区画を目的地にして、壁を見るまで走る（止まらない）<br>・ふさがれた → 次の区画で止まり（前に壁があれば壁合わせ）、計算し直す<br>・途中で U ターンするときは、止まったついでに計算し直す<br>これを繰り返す | `search_check_unknown_walls`、`search_plan_unknown_walls` |
| 4 | **見に行く壁がなくなったら、その場で止まる。止まってから最短経路を計算する**（ここで迷路を Flash にも保存する） | `path_make_shortest` |
| 5 | 帰り：スタートへ戻る（最短走行はスタートから始まるので）。帰りに壁を見ても、4 で計算した最短経路は変わらない | 1 と同じ |

PC テストでは、未知壁探索のあとの最短経路が「全部の壁を知っているときの最短経路」と同じコストになることを、テスト用の迷路 2 つとランダムな迷路 300 個で確かめている（中央 2×2 の迷路：ゴール到着時 196 → 161 = 全部知っているとき 161。止まって計算した回数 16）。

## D. パラメータ違いのコピー → 1 つにまとめる

| KOGUMA | 中身 | まとめ方 |
|---|---|---|
| `Short_NANAME_Move2000` / `2400` / `2700`、`Short_Dijkstra_Move2000` | 約 110 行ずつ。違いはコーナー速度とそれに合わせた旋回パラメータだけ | 旋回パラメータを速度ごとの表（`config/`）にし、最短走行は 1 つの関数にする |
| `main.c` のモード0 No.1〜6 | 「スタート→ゴール→スタート」の流れが 6 回コピーされている | `sys/explore.c` に 1 つだけ書き、違い（探索の種類、全面探索、最後の最短）は設定で渡す |
| `main.c` のモード5〜9 | 旋回テストが速度ごとにコピーされている | 上の C のとおり 1 つのテストモードにする |
| `Motor_trapezoid_PID` / `Motor_NANAME_PID` | `PID_Mode` を書き換えて `Motor_trapezoid` を呼ぶだけ | 壁制御の種類を引数で渡す形にする |

## F. 読んでいて気づいた点（移植時に直す）

- `Failsafe_Motordiff` のしきい値 `motordiff_TH = 100000` は、タイヤ速度（mm/s）に対して大きすぎて、実質的に動作していない。ToraNeko では値を決め直すか、持ち込まない
- `Failsafe_MotorTagetdiff` の「壁に押し付け続けている」判定は、探索速度の範囲（500〜1200mm/s）が直接書かれている。探索速度の設定から決まるようにする
- `pl_callback_getSensor` には、同じ処理をコメントアウトした古い版が残っている。持ち込まない
- `LOG_get_interrupt` は記録する信号が固定（速度、目標、角速度、センサ左右、電圧）。ToraNeko では記録する信号を選べるようにするか、まず同じ構成で持ち込むかをステップ 9 で決める
